# 流浪猫救助档案管理系统 · 答辩 PPT 大纲 v2

> 场景：线下毕业设计 / 实训答辩  
> 受众：指导教师与答辩组老师（.NET 方向）  
> 规模：17 页，约 15 分钟  
> 视觉：暖调手账风，沿用系统配色；右上角大连外国语大学校徽全片固定  
> 事实口径：功能、规模与测试数字均来自本项目文档和已有截图；不使用无出处的行业统计数字

## 一、需求依据与设计判断

- **需求依据**：大纲需包含封面、目录、核心内容和总结页；逐页给出标题、3–5 条要点、论述重点、衔接关系及视觉建议，可直接进入 PPT 制作。
- **结构选择**：采用「PSE 问题—方案—证据」为主叙事，同时保留论文六章页序，方便老师对照论文翻阅。
- **标题策略**：内容页标题尽量写成观点句，17 页标题连读即可形成口头摘要。
- **详略策略**：设计与实现、测试是论证主体；背景只负责建立问题，不铺陈无来源的行业规模。
- **视觉策略**：流程用链路图，规则用状态迁移表，架构用分层图，数据库用实体关系与约束卡，实现用真实截图，测试用结果与覆盖范围说明；每页底部用一句话收束结论。

## 二、整体叙事与时间分配

**一句话主线**：针对救助记录易断链的问题，系统以猫档案为主轴，用状态机约束业务，用三层架构和数据库约束保证落地，再通过页面与测试证明闭环能够运行。

| 部分 | 页码 | 建议时长 | 任务 |
|---|---:|---:|---|
| 开场与目录 | P1–P2 | 1 分钟 | 交代主题、汇报路线与重点 |
| 第一章 绪论 | P3–P4 | 2 分钟 | 证明问题真实、现有工具存在缺口 |
| 第二章 系统分析 | P5–P8 | 4 分钟 | 把缺口转为角色、流程和状态规则 |
| 第三章 系统设计 | P9–P11 | 3 分钟 | 说明规则如何由架构、模块和数据库共同保证 |
| 第四章 系统实现 | P12–P15 | 3.5 分钟 | 用关键页面证明设计已经落地 |
| 第五章 系统测试 | P16 | 1 分钟 | 用用例与主流程测试证明可靠性 |
| 第六章 总结与展望 | P17 | 0.5 分钟 | 总结成果、承认边界、提出加固方向 |

## 三、逐页大纲

### 开场与目录

#### P1｜封面｜流浪猫救助档案管理系统
- 项目全称：流浪猫救助档案管理系统。
- 一句话定位：一只猫从被救助到结案的完整档案链。
- 汇报信息：学生姓名、学号、指导教师、答辩日期。
- 固定识别：右上角放置大连外国语大学校徽。

**论述重点**：先把「档案链」而不是「功能集合」立为全片核心概念。  
**视觉建议**：深棕底、米白大标题、珊瑚橘短线；右侧用低对比圆环做装饰，不使用与主题无关的图库照片。  
**衔接**：由“一条档案链”引出下一页——整条汇报也按这条链展开。

#### P2｜目录｜六章一条线：先讲为什么做，再讲怎么设计，最后证明它能跑
- 六章顺序：绪论、系统分析、系统设计、系统实现、系统测试、总结与展望。
- 论证主线：问题定义 → 规则抽象 → 技术落地 → 运行证据。
- 重点页面：状态机、分层依赖、数据库约束、系统测试。
- 时间分配：设计与实现、测试合计占主要讲述时间。

**论述重点**：目录不仅列章节，还要告诉老师“为什么按这个顺序听”。  
**视觉建议**：2×3 六张章节卡；章节号用珊瑚橘，标题用深棕，页底标注“17 页 / 约 15 分钟”。  
**衔接**：先从第一章回答“现有做法为什么会让档案断掉”。

### 第一章 绪论：建立问题

#### P3｜研究背景｜救助靠微信群和纸笔，猫一换人管，档案就断了
- 记录分散：救助、诊疗、领养信息散落在聊天记录和表格中。
- 关联缺失：同一只猫在不同阶段被重复登记，难以确认是否为同一档案。
- 交接困难：人员变化后，历史处理过程和当前状态难以追溯。
- 核心问题：系统必须能回答“这只猫现在是什么状态、下一步能做什么”。

**论述重点**：痛点不是“没有电子表格”，而是缺少围绕同一只猫持续生长的档案。  
**视觉建议**：三张痛点卡，分别配“分散记录、关联中断、无法追溯”图标；页底用一句话收束为“档案不断链”。  
**衔接**：明确痛点后，再看现有工具为什么只能解决其中一段。

#### P4｜研究现状｜现有工具要么只管发布领养，要么只管看病开药
- 微信群 / 在线表格：成本低、易上手，但没有状态约束与记录关联。
- 领养发布类工具：侧重发布与申请，领养完成后的回访容易失联。
- 宠物医院 HIS：侧重诊疗过程，不负责猫从救助到结案的完整流向。
- 本系统切入点：以猫主档为中心，串联接收、医疗、领养、回访和统计。

**论述重点**：差异不在功能数量，而在是否覆盖“一只猫的完整一生”。  
**视觉建议**：左右对比栏；左侧三类现有工具，右侧本系统的一条完整档案链，不使用无来源的竞品市场数据。  
**衔接**：把“覆盖完整生命周期”的缺口，转成下一页的角色与功能需求。

### 第二章 系统分析：把问题变成规则

#### P5｜需求分析｜两类角色、六个模块，都围绕一张猫主档协作
- 两类角色：管理员负责账号与系统管理，工作人员负责日常救助业务。
- 六个模块：档案、救助接收、医疗、领养、回访、数据统计。
- 页面规模：29 个 ASPX 页面按业务模块组织。
- 协作边界：跨模块通过档案外键关联，不复制多份互不一致的猫信息。
- 权限目标：登录身份与账号角色一致，越权操作在入口处被拦截。

**论述重点**：模块划分服从“一张主表一个业务模块”，避免按页面随意堆功能。  
**视觉建议**：上方两张角色卡，下方六张模块卡；可用功能结构图作备份页，不让缩小后的复杂 UML 挤占正文。  
**衔接**：需求范围确定后，先证明方案在现有条件下做得出来。

#### P6｜可行性分析｜技术、成本、操作三条线都成立，而且都能现场验证
- 技术可行：ASP.NET Web Forms 4.8、C#、SQL Server 与三层架构均为课程技术栈。
- 经济可行：使用现有开发环境即可运行，无额外商业授权依赖。
- 操作可行：母版页统一导航，表单按业务步骤组织，降低学习成本。
- 验证方式：现场检查工程引用、运行关键页面、执行测试用例。

**论述重点**：不停留在“理论上可行”，而是给出答辩现场可检查的证据。  
**视觉建议**：三栏卡片，每栏采用“结论 + 两条证据”；底部放“不引入课程外技术”的收束句。  
**衔接**：可行性成立后，进入系统分析核心——业务究竟怎样流转。

#### P7｜业务流程｜一条主线走完：救助到结案，中间只有两个回退点
- 主流程：建档 → 在站照料 → 健康评估 → 待领养 → 领养登记 → 回访跟踪 → 结案。
- 回退点一：表单校验失败时停在录入页，已填内容保留，已落盘图片需补偿删除。
- 回退点二：办理退养时，档案由已领养退回待领养，领养记录同步置为已退养。
- 一致性要求：业务记录与档案状态在同一事务中更新，避免只改一边。

**论述重点**：主线体现闭环，两个回退点体现异常与逆向操作也被纳入设计。  
**视觉建议**：横向七节点流程图，按状态语义色填充；下方两张回退说明卡，箭头只标主方向，不堆复杂泳道。  
**衔接**：流程说明“会经过哪些状态”，下一页进一步限定“哪些迁移合法、迁移前要满足什么”。

#### P8｜状态机｜5 个状态、7 条迁移，结案必须先有回访
- 五个状态：在站照料、待领养、已领养、已结案、已终止。
- 七条合法迁移：只允许预先定义的迁移路径，不能在状态页任意跳状态。
- 守卫一：待领养到已领养只能由领养登记触发，避免“已领养但无领养人”。
- 守卫二：已领养到已结案要求有效领养下至少一条回访；终止必须填写原因。
- 三层防线：BLL 预检给提示、存储过程加锁复检、数据库 CHECK 约束兜底。

**论述重点**：状态机是业务正确性的核心，不是页面上的一个下拉框。  
**视觉建议**：左侧七行迁移表（迁移 + 触发条件），右侧三张“为什么……”守卫卡；原状态图缩小时文字不可读，可作备份页，不放正文。  
**衔接**：规则已经明确，下一章回答“如何用工程结构保证这些规则不被绕过”。

### 第三章 系统设计：保证规则能落地

#### P9｜系统架构｜四层单向依赖，让界面、规则与数据访问各自收口
- 四层职责：Web 负责交互，BLL 负责业务规则，DAL 负责数据访问，Model 提供共享模型。
- 依赖方向：上层只依赖下层约定，Web 不直接引用 DAL。
- SQL 收口：数据库操作通过存储过程完成，避免 SQL 散落页面代码。
- 结果传递：写操作统一返回 OperationResult，页面据此显示成功或失败原因。

**论述重点**：分层不是目录形式，而是依赖、职责与错误处理都可检查。  
**视觉建议**：左侧四层纵向堆叠图，右侧放共享 Model 与关键工程约定；不使用复杂类图作为正文。  
**衔接**：架构限定层与层的关系，下一页说明这些层如何按业务模块组织。

#### P10｜模块划分｜29 个页面、41 个存储过程，都按同一套模块边界组织
- 六个业务模块与页面一一对应，命名遵循统一前缀。
- BLL 与 DAL 按业务对象拆分，页面不跨层直接处理 SQL。
- 41 个存储过程采用“模块_动作”命名，便于定位与评审。
- 模块间通过主档外键协作，统计只读取业务结果，不回写业务状态。
- 规模证据：页面、业务类、数据类、存储过程可在工程中逐项核对。

**论述重点**：模块表用于证明工程可维护，而不是展示“数量很多”。  
**视觉建议**：四列对照表（模块 / 页面 / 主要职责 / 数据访问），行数控制在 6–7 行；数字只做眉标或合计，不做无意义占比图。  
**衔接**：模块边界解决代码组织，下一页进入数据层，说明状态一致性如何最终落到约束上。

#### P11｜数据库设计｜6 张表、4 对主从，业务规则靠约束写进库里
- 六张表：SysUser、CatArchive、RescueRecord、MedicalRecord、AdoptionRecord、FollowUpRecord。
- 主从关系：CatArchive 是主档，接收、医疗、领养、回访记录围绕其展开。
- 编号约束：UQ_CatArchive_CatNo 保证编号唯一，取号时通过行锁防并发撞号。
- 领养约束：UX_Adoption_OneActive 保证一只猫最多一条有效领养。
- 终止约束：CK_CatArchive_Terminate 保证终止状态与终止原因成对出现。

**论述重点**：即使绕过前端和业务层，数据库仍能拒绝一部分非法数据。  
**视觉建议**：左侧六张表卡突出主表，右侧三张约束卡；详细 ER 图放备份页，避免投影时无法阅读。  
**衔接**：至此完成“流程—规则—架构—数据”的设计论证，下一章用真实页面证明它们已经实现。

### 第四章 系统实现：用页面给出证据

#### P12｜认证与首页｜登录不只是比密码：验证码、加盐哈希与身份一致性共同把关
- 验证码先行：CustomValidator 与 Page.IsValid 先拦截无效提交。
- 密码存储：SHA-256 配合每用户随机盐，数据库不保存明文密码。
- 身份校验：登录时选择的身份必须与账号角色一致。
- 会话最小化：Session 只保存必要的非敏感身份字段。
- 失败提示：统一提示用户名或密码错误，不暴露账号是否存在。

**论述重点**：用登录这一条链路展示安全设计，而不是只展示登录界面。  
**视觉建议**：左侧三组“措施—目的”说明，右侧放登录页与首页概览两张真实截图。  
**衔接**：入口安全之后，进入系统使用频率最高的档案中心。

#### P13｜档案中心｜五项检索、一个事务写两表、详情一次往返拿全
- 列表检索：支持五项条件组合查询，并使用分页控制单次数据量。
- 救助建档：一个事务同时写入档案与接收记录，避免只有半条档案。
- 并发取号：UPDLOCK、HOLDLOCK 配合唯一约束，防止同时建档撞号。
- 详情读取：一次往返返回详情所需字段，减少页面重复查询。
- 状态入口：状态页只开放合法迁移，具体业务动作仍由对应模块触发。

**论述重点**：每个页面截图都对应一个实现难点，截图是证据而非装饰。  
**视觉建议**：2×2 四图墙，分别放列表、建档、详情、状态流转；每张图下用一句话标注技术点。  
**衔接**：档案中心解决“记录得完整”，下一页证明领养后的流程也能闭合。

#### P14｜领养闭环｜登记、退养、回访都在事务里同步改状态
- 领养登记：创建领养记录并把档案改为已领养，同时受唯一有效领养约束。
- 办理退养：领养记录置为已退养，档案同步退回待领养。
- 回访跟踪：回访方式限定为电话、上门或微信，记录归属有效领养。
- 结案条件：至少存在一条有效回访后才允许结案。
- 一致性保证：业务记录和档案状态在同一事务中提交或回滚。

**论述重点**：重点讲“送出去以后仍可追踪”，这才是闭环与一次性登记的差别。  
**视觉建议**：横向三步截图（领养登记 → 回访 → 结案），下方单独放退养反向操作说明条。  
**衔接**：业务闭环产生数据后，下一页说明这些数据如何被汇总成可读指标。

#### P15｜数据统计｜接收、领养、领养率三个数，按月摊开就能看出趋势
- 本年接收：演示环境截图显示 8 只。
- 本年领养：演示环境截图显示 5 只。
- 领养率：演示环境为 62.5%，计算口径为当年领养数 ÷ 当年接收数。
- 月度趋势：按接收日期归月，对比每月接收量与领养量。
- 实现口径：统计逻辑写在存储过程中，页面只负责呈现结果。

**论述重点**：统计不仅展示结果，还要说清时间口径、计算公式与数据来源。  
**视觉建议**：左侧真实统计页截图，右侧三个 KPI 卡（8 / 5 / 62.5%）；必须标注“演示环境数据，非实际救助规模”。  
**衔接**：页面与统计能够运行后，还需要测试证明异常输入和非法迁移同样被拦住。

### 第五章 系统测试：证明不是只在演示路径上能跑

#### P16｜系统测试｜26 个用例全过，绕过前端也写不进脏数据
- 规则类单测：CatRules、PasswordHasher、CaptchaCode 等不连数据库即可验证。
- 鉴权测试：覆盖登录、注册与角色一致性等关键分支。
- 错误映射：SqlErrorMapper 将数据库错误转换为页面可理解的提示。
- 全流程测试：建档、医疗、领养、回访、结案在真实数据库上串联执行。
- 测试规模：8 个测试类、26 个用例；同时说明本机测试环境，避免泛化为生产验证。

**论述重点**：测试同时覆盖纯规则、鉴权异常与完整业务链，而非只测正常登录。  
**视觉建议**：三张测试类型卡 + 底部测试环境条；不使用没有统计依据的覆盖率圆环或质量评分。  
**衔接**：功能、规则与测试证据已经齐备，最后总结完成度和仍未解决的问题。

### 第六章 总结与展望：收束成果与边界

#### P17｜总结与展望｜一条档案链跑通了，剩下的都是加固
- 已完成：从建档到结案的档案链完整跑通，状态与业务记录保持关联。

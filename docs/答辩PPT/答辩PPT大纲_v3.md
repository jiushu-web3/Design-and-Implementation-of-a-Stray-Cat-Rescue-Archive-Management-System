### 第一章 绪论：研究背景与意义 / 国内外研究现状

#### P3｜研究背景与意义｜救助记录容易断链，需要围绕一只猫建立连续档案
- 背景一：救助、诊疗、领养信息散落在聊天记录和表格中。
- 背景二：同一猫的不同阶段缺少统一编号和关联，交接后难以追溯。
- 背景三：状态依赖人工记忆，无法稳定回答“当前状态、下一步能做什么”。
- 业务意义：让接收、医疗、领养、回访形成连续记录，减少重复登记和信息丢失。
- 技术意义：用状态机、事务与数据库约束，把业务规则转化为可验证的系统设计。

**论述重点**：从现实断链问题同时推出业务价值和技术研究价值。  
**视觉建议**：左侧三张背景痛点卡，右侧“业务意义 / 技术意义”双卡；页底收束为“档案不断链”。  
**衔接**：背景说明“为什么值得做”，下一页回答“已有研究和应用做到了哪里”。

#### P4｜国内外研究现状｜已有研究和应用多覆盖局部环节，本项目补齐全流程档案关联

- 国外研究与应用：按论文已有参考文献，归纳机构化收容、领养流程与后续管理等方向【需补具体文献出处】。
- 对比维度：统一主档、状态约束、领养后回访、统计口径四个方面。
- 现有不足：只写参考文献能够支持的结论，不虚构市场规模、产品份额或研究数量。
- 本项目定位：面向校园 / 小型救助场景，以一张猫主档和状态机串联完整业务闭环。

**衔接**：由“需要完整档案关联”的研究定位，进入第二章的角色、需求和流程分析。

### 第二章 系统分析：需求分析 / 可行性分析 / 业务流程

#### P5｜需求分析｜两类角色、六个模块，都围绕一张猫主档协作
- 两类角色：管理员负责账号与系统管理，工作人员负责日常救助业务。
- 六个模块：档案、救助接收、医疗、领养、回访、数据统计。
- 页面规模：29 个 ASPX 页面按业务模块组织。
- 协作边界：跨模块通过档案外键关联，不复制多份不一致的猫信息。
- 权限需求：登录身份与账号角色一致，越权操作在入口处拦截。

**论述重点**：功能需求围绕主档协作展开，而不是按页面随意堆叠。  
**视觉建议**：上方两张角色卡，下方六张模块卡；功能结构图放备份页。  
**衔接**：需求范围确定后，先证明技术、成本和操作条件能够支撑实现。

#### P6｜可行性分析｜技术、成本、操作三条线都成立，而且都能现场验证
- 技术可行：ASP.NET Web Forms 4.8、C#、SQL Server 与分层架构均为课程技术栈。
- 经济可行：使用现有开发环境即可运行，无额外商业授权依赖。
- 操作可行：母版页统一导航，表单按业务步骤组织。
- 验证方式：现场检查工程引用、运行关键页面、执行测试用例。

**论述重点**：可行性必须有可核验证据，不停留在“理论上可行”。  
**视觉建议**：三栏“结论＋证据”卡片，页底注明“不引入课程外技术”。  
**衔接**：条件成立后，进入业务流程，说明一只猫如何从建档走到结案。

#### P7｜业务流程｜一条主线走完：救助到结案，中间只有两个回退点
- 主流程：建档 → 在站照料 → 健康评估 → 待领养 → 领养登记 → 回访跟踪 → 结案。
- 回退点一：表单校验失败停在录入页，保留输入；已落盘图片需补偿删除。
- 回退点二：退养时档案由已领养退回待领养，领养记录同步置为已退养。
- 一致性要求：业务记录与档案状态在同一事务中更新。

**论述重点**：既讲正常主线，也讲异常与逆向操作，证明流程不是理想化单行道。  
**视觉建议**：七节点横向流程图＋两张回退说明卡，按状态语义色区分阶段。  
**衔接**：流程说明经过哪些状态，下一页进一步限定合法迁移及前置条件。

#### P8｜业务流程中的状态规则｜5 个状态、7 条迁移，结案必须先有回访
- 五个状态：在站照料、待领养、已领养、已结案、已终止。
- 七条合法迁移：只允许预定义路径，不能在状态页任意跳转。
- 领养守卫：待领养到已领养只能由领养登记触发。
- 结案与终止守卫：结案要求有效领养下至少一条回访，终止必须填写原因。
- 三层防线：BLL 预检、存储过程加锁复检、数据库 CHECK 约束兜底。

**论述重点**：状态机是业务流程能够正确执行的规则内核。  
**视觉建议**：左侧七行迁移表，右侧三张“为什么……”守卫卡；复杂状态图放备份页。  
**衔接**：业务规则明确后，第三章说明架构、模块和数据库如何共同保证规则落地。

### 第三章 系统设计：系统架构 / 功能模块 / 数据库

#### P9｜系统架构｜四层单向依赖，让界面、规则与数据访问各自收口
- 四层职责：Web 负责交互，BLL 负责规则，DAL 负责数据访问，Model 提供共享模型。
- 依赖方向：上层只依赖下层约定，Web 不直接引用 DAL。
- SQL 收口：数据库操作通过存储过程完成。
- 结果传递：写操作统一返回 OperationResult，页面显示成功或失败原因。

**论述重点**：分层不仅是目录形式，而是依赖、职责与错误处理都可检查。  
**视觉建议**：四层纵向堆叠图＋共享 Model 与工程约定说明，不使用缩小后难读的复杂类图。  
**衔接**：架构限定层间关系，下一页说明功能模块如何在这些层中组织。

#### P10｜功能模块｜29 个页面、41 个存储过程，都按同一套模块边界组织
- 六个业务模块与页面一一对应，命名遵循统一前缀。
- BLL 与 DAL 按业务对象拆分，页面不跨层直接处理 SQL。
- 41 个存储过程采用“模块_动作”命名，便于定位与评审。
- 模块间通过主档外键协作，统计只读业务结果，不回写业务状态。
- 规模证据：页面、业务类、数据类和存储过程可在工程中逐项核对。

**论述重点**：模块表证明职责清晰和可维护，不是为了展示数量。  
**视觉建议**：模块 / 核心功能 / 对应页面 / 数据访问四列对照表，控制在 6–7 行。  
**衔接**：模块解决代码组织，下一页说明状态一致性最终如何写入数据库约束。

#### P11｜数据库｜6 张表、4 对主从，业务规则靠约束写进库里
- 六张表：SysUser、CatArchive、RescueRecord、MedicalRecord、AdoptionRecord、FollowUpRecord。
- 主从关系：CatArchive 为主档，接收、医疗、领养、回访记录围绕其展开。
- 编号约束：UQ_CatArchive_CatNo 保证唯一，取号时通过行锁防并发撞号。
- 领养约束：UX_Adoption_OneActive 保证一只猫最多一条有效领养。
- 终止约束：CK_CatArchive_Terminate 保证终止状态与终止原因成对出现。

**论述重点**：即使绕过前端和业务层，数据库仍能拒绝部分非法数据。  
**视觉建议**：六张表卡突出主表＋三张约束卡；完整 ER 图放备份页。  
**衔接**：设计论证完成，第四章按“核心功能＋核心页面”逐项展示实现证据。

### 第四章 系统实现：核心功能 / 核心页面

#### P12｜认证与首页｜核心功能是入口安全，核心页面是登录页与首页
- 核心功能一：验证码与 Page.IsValid 先拦截无效提交。
- 核心功能二：SHA-256 配合每用户随机盐，数据库不保存明文密码。
- 核心功能三：登录身份与账号角色一致，Session 只保存必要非敏感字段。
- 核心页面：登录页展示验证与统一失败提示，首页展示登录后的业务入口。
- 安全边界：失败提示不区分账号是否存在，避免暴露账号信息。

**论述重点**：页面上看到的登录流程，对应背后完整的认证与权限措施。  
**视觉建议**：左侧“核心功能”三组措施，右侧“核心页面”登录页与首页两张实拍。  
**衔接**：入口安全之后，进入使用频率最高的档案中心。

#### P13｜档案中心｜核心功能是检索、建档与状态控制，核心页面是列表、建档、详情和状态页
- 列表页：五项条件组合检索，并通过分页控制单次数据量。
- 建档页：一个事务同时写档案与接收记录，避免半条档案。
- 并发控制：UPDLOCK、HOLDLOCK 配合唯一约束，防止同时建档撞号。
- 详情页：一次往返返回详情所需字段，减少重复查询。
- 状态页：只开放合法迁移，具体业务动作由对应模块触发。

**论述重点**：每张页面截图都对应一个功能点或实现难点。  
**视觉建议**：2×2 四图墙，每图下用“核心功能—技术实现”一句话标注。  
**衔接**：档案中心保证记录完整，下一页证明领养后的流程仍能闭合。

#### P14｜领养闭环｜核心功能是登记、退养、回访与结案，核心页面展示完整闭环
- 领养登记页：创建领养记录并把档案改为已领养，受唯一有效领养约束。
- 退养操作：领养记录置为已退养，档案同步退回待领养。
- 回访页：回访方式限定为电话、上门或微信，记录归属有效领养。
- 结案操作：至少存在一条有效回访后才允许结案。
- 一致性保证：业务记录和档案状态在同一事务中提交或回滚。

**论述重点**：强调领养后的持续追踪，而不是只完成一次登记。  
**视觉建议**：领养登记 → 回访 → 结案三步截图，下方单独放退养反向操作说明条。  
**衔接**：业务闭环产生数据，下一页展示统计功能及统计页面。

#### P15｜数据统计｜核心功能是统一口径汇总，核心页面是统计看板
- 本年接收：演示环境截图显示 8 只。
- 本年领养：演示环境截图显示 5 只。
- 领养率：演示环境为 62.5%，口径为当年领养数 ÷ 当年接收数。
- 月度趋势：按接收日期归月，对比每月接收量与领养量。
- 实现方式：统计逻辑写在存储过程中，统计页面只负责呈现结果。

**论述重点**：统计功能必须同时交代时间口径、公式和数据来源。  
**视觉建议**：左侧统计页实拍，右侧 8 / 5 / 62.5% 三个 KPI 卡；图注标明“演示环境数据，非实际救助规模”。  
**衔接**：核心功能与页面能够运行后，第五章用功能测试用例和结果验证正确性。

### 第五章 系统测试：功能测试用例 / 测试结果

#### P16｜系统测试｜用例覆盖正常、异常与主流程，26 个用例全部通过
- 功能测试用例一：登录、注册、角色一致性，覆盖正确输入、错误凭证和身份不匹配。
- 功能测试用例二：建档、状态迁移、领养、回访、结案，覆盖合法操作与非法迁移。
- 规则与异常用例：CatRules、PasswordHasher、CaptchaCode、SqlErrorMapper 等类分别验证规则与错误提示。
- 全流程用例：在真实数据库上串联建档、医疗、领养、回访和结案。
- 测试结果：8 个测试类、26 个用例全部通过；测试环境为本机 Windows、SQL Server 与浏览器环境，不泛化为生产验证。

**视觉建议**：左侧五行功能用例表（测试项 / 代表场景 / 预期结果 / 实测结果），右侧 26/26 结果卡与测试环境；不使用无依据的覆盖率圆环。

### 第六章 总结展望：工作总结 / 不足与展望

#### P17｜总结展望｜一条档案链跑通了，不足都有明确的加固方向
- 工作总结一：从建档到结案的档案链完整跑通，状态与业务记录保持关联。
- 工作总结二：四层分离、29 个页面、41 个存储过程按模块落地。
- 工作总结三：26 个用例覆盖规则、鉴权和完整主流程。
- 不足与展望一：InProc 会话不适合多机部署 → 后续升级为分布式会话方案。
- 不足与展望二、三：单轮 SHA-256 安全性不足 → 升级 PBKDF2；缺少操作审计 → 增加审计表与关键动作日志。

**论述重点**：总结不只是重复成果，还要把每项不足和对应改进方案一一说清。  
**视觉建议**：深棕底与封面呼应；左侧“工作总结”，右侧“不足 → 展望”三组对应卡，下方放致谢语。

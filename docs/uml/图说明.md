## 图 4-2　系统用例图

**建议位置**：第 4 章 概要设计 → 4.x 用例分析

**参与者**

| 参与者 | 判定依据 | 权限边界 |
|---|---|---|
| 工作人员 | `RoleCodes.Staff = 2` | 除统计、用户管理外的全部用例 |
| 管理员 | `RoleCodes.Admin = 1` | 工作人员全部用例 + 统计报表 + 用户管理 |

两个参与者的关系是**泛化**：`AdminPageBase : PageBase`（代码里就是继承），管理员天然拥有工作人员的用例，
所以图中不需要给管理员重复画 11 条连线。`AdminPageBase.OnInit` 里 `user.Role != RoleCodes.Admin` 就跳 `Default.aspx?msg=forbidden`。

**14 个用例与页面的对应**

| 用例 | 页面 | 关键实现 |
|---|---|---|
| 登录系统 | Login.aspx | `UserBll.Login` → 加盐哈希比对 |
| 修改密码 | ChangePassword.aspx | `UserBll.ChangePassword`（要验旧密码） |
| 查看首页概览 | Default.aspx | `CatBll.GetHomeCounts` + `GetRecent` |
| 查询救助档案 | CatList.aspx | `CatBll.Search`：关键词 + 状态 + 性别 + 救助日期区间 + 分页 |
| 建立救助档案 | CatAdd.aspx | `CatBll.Create`（档案 + 救助信息一个事务） |
| 维护救助档案 | CatEdit / RescueEdit | `CatBll.Update` / `UpdateRescue` |
| 变更档案状态 | CatStatus.aspx | `CatBll.ChangeStatus` |
| 登记医疗记录 | MedicalAdd | `MedicalBll.Add` |
| 登记领养 | AdoptionAdd | `AdoptionBll.Add` |
| 办理退养 | AdoptionDetail | `AdoptionBll.Return` |
| 记录回访 | FollowUpAdd | `FollowUpBll.Add` |
| 查看统计报表 | Stat.aspx | `StatBll.Monthly`（**仅管理员**） |
| 管理系统用户 | UserList / Add / Edit | `UserBll.*`（**仅管理员**） |

**«include» 的两条线怎么讲**
> 登记领养和办理退养都不是单纯插一条记录：领养成功后档案状态要变成「已领养」，
> 退养后要退回「待领养」。这一步由存储过程在同一个事务里完成，所以建模成包含关系。

## 图 4-3　系统实体类图

**建议位置**：第 4 章 概要设计 → 4.x 数据库与实体设计

**六大实体 → 六张表**（`Database/02_CreateTables.sql`）

| 实体 | 表 | 主键 | 关键外键 / 约束 |
|---|---|---|---|
| SysUser | SysUser | UserId | `UQ_SysUser_UserName`、`CK_SysUser_Role IN (1,2)` |
| CatArchive | CatArchive | CatId | `UQ_CatArchive_CatNo`、`CK_CatArchive_Status IN (1..5)`、`CK_CatArchive_Terminate` |
| RescueRecord | RescueRecord | RescueId | `UQ_RescueRecord_CatId`（1:1）、`CK_RescueRecord_FoundWay` |
| MedicalRecord | MedicalRecord | MedicalId | `FK_MedicalRecord_CatArchive` |
| AdoptionRecord | AdoptionRecord | AdoptionId | `UX_Adoption_OneActive`（唯一筛选索引） |
| FollowUpRecord | FollowUpRecord | FollowUpId | `FK_FollowUpRecord_AdoptionRecord`、`CK_FollowUpRecord_FollowWay` |

**关系与多重性**

| 关系 | 多重性 | 类型 | 依据 |
|---|---|---|---|
| SysUser — CatArchive | 1 : 0..* | 关联 | `CatArchive.CreateUserId` |
| CatArchive — RescueRecord | 1 : 1 | 组合 | `UQ_RescueRecord_CatId` 唯一约束 |
| CatArchive — MedicalRecord | 1 : 0..* | 组合 | 一次救助可有多条诊疗 |
| CatArchive — AdoptionRecord | 1 : 0..* | 组合 | 退养后再领养会产生第二条 |
| AdoptionRecord — FollowUpRecord | 1 : 0..* | 组合 | `FollowUpRecord.AdoptionId` |

**为什么是组合而不是普通关联**
> 子记录脱离主档案没有独立业务意义，而且删除档案时存储过程会连同子表一起处理，
> 生命周期完全绑定，所以用实心菱形。

**描述要点**
- 属性按数据库字段顺序排，类型做了 C# 映射：`TINYINT→byte`、`DATETIME→DateTime`、可空列加 `?`。
- `AdoptionRecord.FollowUpCount` 不是表字段，是 `usp_Adoption_ListByCat` 里 `COUNT` 出来的派生属性（画在方法区）。

## 图 4-4　系统分层类图

**建议位置**：第 4 章 概要设计 → 4.x 系统架构设计

**三层与依赖方向**

```
页面（.aspx / .aspx.cs）
   ↓ 只引用
StrayCat.BLL    CatBll / MedicalBll / AdoptionBll / FollowUpBll / UserBll / StatBll
                + 规则类 CatRules / FieldRules / PasswordHasher
   ↓ 只引用
StrayCat.DAL    CatDal / MedicalDal / AdoptionDal / FollowUpDal / UserDal / StatDal / DbHelper
   ↓
SQL Server      38 个存储过程
```

**说明要点**
1. 页面只 `new CatBll()`，从不 `new CatDal()`；`CatBll` 的构造函数接受 `CatDal` 参数，是为了单元测试能注入假对象（`StrayCat.Tests` 就是这么做的）。
2. 所有写操作方法返回 `OperationResult<T>`，成功/失败由 `Success` + `Message` 表达，页面不写 try-catch。
3. `CatRules` 是静态类，只吃不改：入参是状态码，出参是 bool 或错误消息，便于单测（`CatRulesTests.cs` 覆盖了它）。
4. `DbHelper` 的 5 个方法覆盖了全部访问形态：列表查询、分页查询、取单值、取新增主键、执行写操作。

**BLL 与 DAL 的方法数量（可写进论文做规模说明）**

| 层 | 类数 | 公开方法数（约） |
|---|---|---|
| BLL | 9 | 40 |
| DAL | 7 | 34 |

## 图 4-5　救助与领养主流程活动图

**建议位置**：第 4 章 概要设计 → 4.x 业务流程设计

**三条泳道的职责划分**

| 泳道 | 职责 | 对应实现 |
|---|---|---|
| 工作人员 | 录入信息、做业务决策（评估是否通过、是否退养） | 页面表单 + 按钮 |
| 系统（页面与业务层） | 校验、编号生成、状态判定 | `FieldRules` / `CatRules` / `Page.IsValid` |
| 数据库 | 事务写入、状态字段更新 | `05_BusinessProcedures.sql` |

**流程节点与代码的对应**

| 活动 | 实现位置 |
|---|---|
| 验证控件与服务端规则校验 | `CatAdd.aspx` 的 `RequiredFieldValidator` + `CatBll.Create` 内的 `FieldRules.First(...)` |
| 生成档案编号 | `usp_Cat_CreateWithRescue` 里 `CAT + YEAR + RIGHT('0000'+seq,4)` |
| 事务写入两表 | 同一存储过程的 `BEGIN TRAN … COMMIT` |
| 校验状态为待领养 | `CatRules.CanAddAdoption` + 存储过程 `IF @Status <> 2` |
| 事务写入领养记录并改状态 | `usp_Adoption_Create` |
| 退养后状态回退 | `usp_Adoption_Return`（档案 3→2） |
| 有效回访 > 0 才能结案 | `CatRules.ChangeStatus` 的 `activeFollowUpCount > 0` 判断 |

**描述要点**
- 重点讲两个「回退」：表单失败回退到录入、退养回退到待领养。这两个回退就是「状态机」在流程上的体现。
- 结案前必须先有回访，这条约束把「回访模块」和「档案模块」绑在一起，也解释了为什么回访表挂在领养记录下面。

## 图 4-6　档案状态流转图

**建议位置**：第 4 章 概要设计 → 4.x 状态设计（也可放详细设计）

**五个状态**（`StrayCat.Model/CatStatuses.cs`）

| 值 | 常量 | 含义 |
|---|---|---|
| 1 | `InCare` | 在站照料 |
| 2 | `WaitingAdoption` | 待领养 |
| 3 | `Adopted` | 已领养 |
| 4 | `Closed` | 已结案（终态） |
| 5 | `Terminated` | 已终止（终态） |

**七条迁移与守卫条件**

| # | 迁移 | 事件 | 守卫条件 | 代码 |
|---|---|---|---|---|
| 1 | 初始 → 在站照料 | 建立救助档案 | — | `usp_Cat_CreateWithRescue` 固定写 1 |
| 2 | 在站照料 → 待领养 | 健康评估通过 | — | `CatRules.ChangeStatus` |
| 3 | 待领养 → 在站照料 | 退回继续照料 | — | 同上 |
| 4 | 待领养 → 已领养 | 登记领养 | 领养人信息完整、无有效领养 | `CanAddAdoption` + `usp_Adoption_Create` |
| 5 | 已领养 → 待领养 | 办理退养 | 退养原因必填 | `usp_Adoption_Return` |
| 6 | 已领养 → 已结案 | 结案 | 有效回访次数 > 0 | `CatRules.ChangeStatus` 返回 `FollowUpRequired` |
| 7 | 在站照料/待领养 → 已终止 | 终止 | 终止原因必填 | 同上 + `CK_CatArchive_Terminate` |

**「不允许」的迁移**（答辩很可能问「能不能从已结案改回待领养」）
> 不能。`CatStatuses.IsClosed(4 或 5)` 为真，`CatRules` 的所有 `Can*` 方法都返回 false，
> 页面上编辑、删除、加医疗、加领养按钮全部置灰。数据库层面 `CK_CatArchive_Terminate` 还会校验
> 「状态=5 时必须有终止原因，否则必须为 NULL」。

## 图 5-1　救助建档顺序图

**建议位置**：第 5 章 详细设计 → 5.x 救助建档模块

**7 条生命线与消息序列**

| # | 消息 | 代码位置 |
|---|---|---|
| 1 | 填写并提交 | `CatAdd.aspx` 表单 `SaveButton_Click` |
| 2 | 验证控件 + `Page.IsValid` | `CatAdd.aspx` 标记 + `if (!Page.IsValid) return;` |
| 3 | `Create(cat, rescue, userId)` | `CatBll.Create` |
| 4 | `First(ValidateArchive, ValidateRescue)` | `CatBll.ValidateArchive` / `ValidateRescue` |
| 5 | 返回 null（校验通过） | `FieldRules.First` |
| 6 | `OperationResult.Fail(msg)` | alt 分支 |
| 7 | `DeletePhoto()` | `PageHelper.DeletePhoto`（已存图要清掉） |
| 8 | `Create(cat, rescue)` | `CatDal.Create` |
| 9 | `ExecuteReturnId("usp_Cat_CreateWithRescue")` | `DbHelper.ExecuteReturnId` |
| 10 | `EXEC` 存储过程 | `Database/05_BusinessProcedures.sql` |
| 11 | `BEGIN TRAN … COMMIT` | 编号生成 + 两次 INSERT |
| 12 | 返回 `@CatId` | `SCOPE_IDENTITY()` |
| 13 | 重定向到详情页 | `Leave("CatDetail.aspx?id=" + result.Data)` |

**三个可讲的细节**
1. **图片的补偿删除**：图片在业务校验之前就落盘了，一旦校验失败必须删，否则磁盘上留垃圾文件。
2. **编号并发的处理**：`SELECT MAX(...) WITH (UPDLOCK, HOLDLOCK)` 把取号锁在事务里，两个人同时建档也不会撞号。
3. **一个事务写两张表**：`CatArchive` 和 `RescueRecord` 必须同时成功，否则档案没有救助信息，属于脏数据。

## 图 5-2　领养登记顺序图

**建议位置**：第 5 章 详细设计 → 5.x 领养管理模块

**关键点**

| 环节 | 说明 |
|---|---|
| 先读档案 | `CatDal.GetDetail` 拿到当前状态和救助日期 |
| 规则判定 | `CatRules.CanAddAdoption(status)` —— 只有状态 2 才允许 |
| 日期校验 | `FieldRules.NotBefore(adoptDate, rescueTime)` —— 领养不能早于救助 |
| 状态复查 | 存储过程 `IF @Status <> 2 RAISERROR` —— 防止两次请求之间状态被别人改了 |
| 唯一性 | `UX_Adoption_OneActive` 唯一索引（`WHERE Status = 1`） |
| 状态联动 | `UPDATE CatArchive SET Status = 3` 在同一事务 |

**为什么状态要判两次**
> BLL 判一次是为了给用户友好提示（返回 `Messages.StatusNotAllowed`），
> 存储过程判一次是为了防止并发：两个工作人员同时给同一只猫登记领养，
> 后到的那个必须被挡住。“先查后改”中间有时间窗口，数据库层的锁和唯一索引才是最后一道防线。

## 答辩可能被追问的问题

| 问题 | 回答要点 |
|---|---|
| 为什么用 Web Forms 不用 MVC？ | 课程方向是 .NET Web Forms；母版页 + 服务器控件 + 验证控件在表单密集的管理系统里开发效率高；状态保存在 ViewState，页面间用 Session 传当前用户。 |
| 三层架构的「层」体现在哪？ | 4 个独立项目：Model / DAL / BLL / Web，引用方向单向，Web 不引用 DAL。 |
| 为什么用存储过程而不是拼 SQL？ | 防注入（参数化）、把事务放在数据库端、改 SQL 不用重新编译网站。全站 38 个存储过程。 |
| 状态机是怎么保证不会乱的？ | 三层：`CatRules` 统一判定 → 存储过程复查并加锁 → 数据库 `CHECK` 约束兜底。 |
| 并发怎么处理？ | `UPDLOCK, HOLDLOCK` 锁行 + 唯一索引 `UX_Adoption_OneActive` + `SET XACT_ABORT ON`。 |
| 有没有做测试？ | `StrayCat.Tests` 26 个用例，覆盖规则类、密码哈希、SQL 错误映射、登录鉴权、业务流程。 |
| 图是你自己画的吗？ | 图依据 `gen_uml.py` 生成，代码与图一一对应；可以现场打开 `CatRules.cs` 对照状态图讲。 |

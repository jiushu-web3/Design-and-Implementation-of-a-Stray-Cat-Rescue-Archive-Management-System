# 流浪猫救助档案管理系统 总体设计

- 日期：2026-11-12
- 状态：总体设计，待评审
- 范围：覆盖课题要求的全部 11 个功能模块
- 技术栈：ASP.NET Web Forms（.NET Framework 4.8）+ 三层架构 + SQL Server 存储过程

## 1. 系统定位与角色

面向动物救助机构及有领养意愿的社会公众，为流浪猫建立从发现、救助、治疗、绝育、寄养到领养的全过程电子档案，并提供内容发布与宠物用品商城。

| 角色 | 说明 | 主要能力 |
| --- | --- | --- |
| 管理员 | 救助站工作人员 | 全部档案、救助、健康、绝育免疫、寄养、领养审核、回访、内容发布、商品与订单管理、用户管理、统计报表 |
| 领养人 | 注册的社会公众 | 浏览公告/科普/待领养猫/商品，上报流浪猫，提交领养申请，查看自己的记录，购物下单与查询订单 |

角色值沿用现有约定：`Admin = 1`、`User = 2`（原 `Staff` 改名为 `User`，值不变）。

权限规则：

- 公开内容（公告、文章、待领养列表、商品列表）不登录可浏览。
- 所有写操作（上报、申请、下单、购物车）需登录。
- 管理页统一继承 `AdminPageBase`；领养人页面继承 `PageBase`。

## 2. 模块划分与实施顺序

| 阶段 | 模块 | 表 | 说明 |
| --- | --- | --- | --- |
| 一 | 角色与 C 端入口 | `StrayReport`、`AdoptionApplication` | 权限收回、上报审核、领养申请审核（已有独立设计） |
| 二 | 机构侧档案深化 | `FosterRecord`、`SterilizationRecord`、`MedicalRecord` 扩展 | 品种字段、健康分类、绝育免疫、寄养照护 |
| 三 | 内容发布 | `ArticleCategory`、`Article` | 公告、科普资讯、领养信息、宠物知识统一为文章模型 |
| 四 | 商城 | `ProductCategory`、`Product`、`Cart`、`CartItem`、`Order`、`OrderItem` | 商品浏览、购物车、下单、模拟付款、取消待付款订单 |
| 五 | 查询与统计 | 无新表 | 复合条件查询、分页、报表补强 |

每个阶段独立设计、独立实现、独立验收，前四个阶段都建立在现有三层结构上，不引入新框架。

## 3. 总体架构

```text
浏览器
  ├─ 公开页面 ──────────────┐
  ├─ 领养人页面（PageBase）─┤
  └─ 管理页面（AdminPageBase）┴─► 页面 Code-Behind
                                    → BLL（校验、状态机、业务规则）
                                        → DAL（参数、行映射）
                                            → DbHelper
                                                → 存储过程（事务、约束）
                                                    → SQL Server
```

保持不变的分层约束：

- 页面不出现 SQL，不直接引用 DAL。
- BLL 负责字段校验与状态判断，DAL 只做存储过程调用与映射。
- 跨表写操作放在存储过程事务里，例如审核通过时同时生成领养记录并改猫状态。
- 中文提示统一放 `Messages`，模型与常量放 `StrayCat.Model`。

## 4. 数据模型全景

保留现有 6 张表：`SysUser`、`CatArchive`、`RescueRecord`、`MedicalRecord`、`AdoptionRecord`、`FollowUpRecord`。新增 12 张表，总计 18 张。

### 4.1 现有表的最小扩展

| 表 | 扩展 | 原因 |
| --- | --- | --- |
| `CatArchive` | 增加 `Breed NVARCHAR(50) NULL` | 课题要求“品种”，现有 `Color` 只表示毛色 |
| `MedicalRecord` | 增加 `RecordType TINYINT NOT NULL DEFAULT 1`、`NextDate DATE NULL` | 区分体检/疾病/治疗/驱虫，支持下次复查提醒 |
| `AdoptionRecord` | 增加 `AgreementNo NVARCHAR(30) NULL`、`SignDate DATE NULL`、`AgreementPath NVARCHAR(200) NULL` | 领养协议信息 |

`RecordType` 取值：1 体检、2 疾病治疗、3 驱虫、4 其他。疫苗与绝育手术统一放 `SterilizationRecord`。

### 4.2 新增表

| 表 | 关键字段 | 关系 |
| --- | --- | --- |
| `StrayReport` | 上报人、地点、时间、描述、照片、电话、状态、驳回理由、CatId | N:1 `SysUser`；审核通过后 1:1 `CatArchive` |
| `AdoptionApplication` | 猫、申请人、姓名、电话、住址、理由、状态、驳回理由、AdoptionId | N:1 `CatArchive`、`SysUser`；通过后 1:1 `AdoptionRecord` |
| `SterilizationRecord` | 猫、手术日期、医院、费用、疫苗名称、接种日期、放归日期、放归地点、备注 | N:1 `CatArchive` |
| `FosterRecord` | 猫、寄养人、电话、开始/结束日期、喂养情况、清洁情况、异常情况、备注 | N:1 `CatArchive` |
| `ArticleCategory` | 名称、类型、排序、启用 | 1:N `Article` |
| `Article` | 分类、标题、摘要、正文、封面、关键词、是否发布、发布时间、浏览量 | N:1 `ArticleCategory` |
| `ProductCategory` | 名称、排序、启用 | 1:N `Product` |
| `Product` | 分类、名称、价格、库存、图片、描述、上下架 | N:1 `ProductCategory` |
| `Cart` | 用户、创建时间 | 1:1 `SysUser`；1:N `CartItem` |
| `CartItem` | 购物车、商品、数量 | N:1 `Cart`、`Product` |
| `Order` | 订单号、用户、总金额、状态、支付时间、创建时间 | N:1 `SysUser`；1:N `OrderItem` |
| `OrderItem` | 订单、商品、商品名快照、单价快照、数量、小计 | N:1 `Order`、`Product` |

### 4.3 主要外键关系（对应课题要求）

```text
CatArchive 1 ── 1 RescueRecord
CatArchive 1 ── N MedicalRecord
CatArchive 1 ── N SterilizationRecord
CatArchive 1 ── N FosterRecord
CatArchive 1 ── N AdoptionRecord
CatArchive 1 ── N AdoptionApplication
AdoptionRecord 1 ── N FollowUpRecord
ArticleCategory 1 ── N Article
ProductCategory 1 ── N Product
SysUser 1 ── 1 Cart ── N CartItem ── N:1 Product
SysUser 1 ── N Order ── N OrderItem ── N:1 Product
```

`ArticleCategory.Type`（公告/科普/领养信息/宠物知识）区分内容类型，避免为四类内容建四套结构相同的表；课题要求的“知识分类与知识文章”主外键即 `ArticleCategory` → `Article`。

### 4.4 关键约束

- 一只猫同时只能有一条有效领养：`AdoptionRecord` 上保留现有筛选唯一索引。
- 同一用户对同一只猫只能有一条待审核申请：`AdoptionApplication` 筛选唯一索引。
- 同一用户只有一辆购物车：`Cart.UserId` 唯一。
- 订单号唯一：`Order.OrderNo` 唯一；订单状态：1 待付款、2 已付款、3 已取消。
- 商品价格与名称在下单时写入 `OrderItem` 快照，商品后续改价不影响历史订单。
- `Order` 只允许“待付款 → 已付款”或“待付款 → 已取消”，取消时回补库存（可选，见第 8 节）。

## 6. 核心流程

### 6.1 上报 → 建档

```text
领养人提交上报（状态 1 待审核）
  → 管理员审核
      ├─ 采纳：补全档案字段 → 事务内生成 CatArchive + RescueRecord → 回写 CatId
      └─ 驳回：填写理由
```

### 6.2 申请 → 领养

```text
领养人对“待领养”猫提交申请（状态 1 待审核）
  → 管理员审核
      ├─ 通过：事务内生成 AdoptionRecord、猫改为“已领养”、回写 AdoptionId
      └─ 驳回：填写理由
  → 管理员补录领养协议信息
  → 按计划新增回访记录
```

### 6.3 购物 → 下单 → 付款

```text
加入购物车（同一商品累加数量）
  → 结算：校验库存与上架状态，生成 Order + OrderItem 快照，状态 1 待付款
  → 模拟付款：状态 1 → 2，记录 PayTime，扣减库存
  → 取消：仅状态 1 可取消，状态 → 3，回补库存
```

### 6.4 内容发布

```text
管理员在分类下新建文章 → 保存草稿 → 发布（PublishTime）
  → 公开列表按分类/关键词/时间分页展示 → 详情页浏览量 +1
```

## 7. 查询与统计

统一沿用 `DbHelper.QueryPage` 与存储过程的 `@TotalCount` 输出参数。

| 查询 | 条件 |
| --- | --- |
| 档案 | 编号/名字模糊、状态、性别、是否绝育、日期范围，复合分页 |
| 健康 | 猫、记录类型、日期范围 |
| 领养申请 | 状态、猫、申请人，管理员与“我的申请”共用 |
| 订单 | 状态、订单号、日期范围；用户侧只看自己的 |
| 商品 | 分类、关键词、价格区间、上架状态 |
| 文章 | 分类、关键词（标题/摘要/正文）、发布时间 |

统计报表：月度救助数、月度领养数、在站/待领养/已领养数量、寄养中数量、健康支出合计、商品销量与订单金额。图表用现有页面内嵌 SVG 或轻量脚本实现，不引入前端框架。

## 8. 非功能与边界

- 图片：复用现有保存逻辑，单图、限制 2MB，文件名加时间戳；商品图与文章封面同样处理。
- 事务：审核、下单、付款、取消均在存储过程内完成，使用 `XACT_ABORT ON` 与行锁。
- 并发：库存扣减用条件更新（`Stock >= @Qty`），失败提示“库存不足”。
- 安全：密码继续 SHA-256 + 盐；领养人不可访问管理页；订单与申请只能查看自己的数据（按 `UserId` 过滤）。
- 兼容：所有数据库变更为增量脚本（`08_*.sql` 起），不修改已执行的历史脚本。
- 不做：真实支付、物流跟踪、优惠券、退款流程、多规格商品、评论系统。

## 9. 实施顺序与验收

| 阶段 | 交付 | 验收 |
| --- | --- | --- |
| 一 | 角色权限 + 上报 + 领养申请 | 领养人无法进入管理页；上报与申请经审核后正确生成档案/领养记录 |
| 二 | 档案深化 + 健康分类 + 绝育免疫 + 寄养 | 三类记录可增删改查，与猫档案正确关联 |
| 三 | 文章分类与文章发布 | 四类内容可发布、浏览、关键词查询 |
| 四 | 商城全流程 | 购物车合并数量、下单快照、模拟付款、取消回补库存 |
| 五 | 查询与统计 | 复合条件分页查询正确；统计数字与明细一致 |

每个阶段完成后运行现有 xUnit 测试并补充对应单元测试，页面改动做手工回归。
